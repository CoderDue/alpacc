# testcuda.sh random-grammar failure (open bug)

## Summary

`tests/testcuda.sh` intermittently fails on grammars generated by
`alpacc random` at (BS=128, IPT=2), reporting `Unable to parse` on the
smallest generated input (typically `"aaaa"`, 4 bytes, single block).

The failure is not caused by the fused ★-monoid lookback pass — single-block
inputs never traverse `fusedLookback` past block 0's fast path.  The
underlying bug is likely pre-existing in the CUDA lexer's block-0 handling
of short inputs, or in an interaction between codegen and specific random
grammar shapes.

## Reproduction

```bash
# In nix-shell (parallel is a shell.nix dep):
bash tests/testcuda.sh 1 1 5 1 --lexer
```

Failure looks like:

```
===== FAIL: batch BS=128 IPT=2, job 1 =====
params {
  lookback=1.
  lookahead=1.
}

a = /(\x63|(\x61|(\x63|\x61)))/.
b = /( \x63)/.
c = /\x62/.
A -> a.
B -> c A b a a b.
B -> a b A c.

Failed on Input: "aaaa"
Input Index: 0
Expected: (T "a",(0,1)) (T "a",(1,2)) (T "a",(2,3)) (T "a",(3,4))
Got: Unable to parse.
```

The exact grammar changes per run because `alpacc random` reseeds every
invocation; the failing input is nearly always `"aaaa"` at index 0.

## What we know

- The failing config is always the **first** in testcuda's (BS, IPT) sweep,
  BS=128 IPT=2.  Later configs in the sweep aren't reached because the
  script bails on first fail (`break 2`).
- Confirmed on `main` at merge commit `64444f4` (which brings fusion +
  sparse endo repr onto main).
- `alpacc test compare` returns "Unable to parse" — meaning the CUDA
  binary produced `valid = 0` for that test case.  Concretely
  `!ctx.isOverflow() && ctx.isAccept()` evaluated to false.
- Direct standalone reproduction with the same grammar text and inputs
  file `alpacc test generate --length 4` produces **passing** output.
  The failure only shows up inside testcuda.sh's driver loop.

## Hypotheses

1. **Random-seed effect**: `alpacc random` and `alpacc test generate` are
   time/PRNG-seeded.  The failing `.inputs` file testcuda generated in the
   failing run is not what standalone re-generation produces, so the
   attempt to reproduce standalone tests a different corpus.  If true, the
   bug is a specific input in the .inputs file that doesn't survive
   regeneration.
2. **Pre-existing lexer bug at short inputs**: block 0 fast path may
   mishandle inputs shorter than the tile size (128 * 2 = 256 tokens),
   with block-0-specific accept/overflow logic.  This would be unrelated
   to the fusion work and predates it.
3. **Codegen non-determinism**: a specific grammar shape may compile to
   codegen that miscomputes the accept table.  If so, running `alpacc
   cuda` on the exact failing grammar text (recovered from log) should
   deterministically produce a broken binary.

## Ruling in / out fusion

Fusion is **not** implicated because `fusedLookback` is called from Phase
B; block 0 returns from `fusedLookback` at the fast-path (lines 471-489 in
`backends/cuda/lexer.cu` post-fix).  For a single-block input, no
inter-block synchronization happens.  The bug is upstream of the fold
formula, downstream of Phase A, or in block-0-specific accept detection.

## Reproducing progress

- On `main` (`64444f4`), `bash tests/testcuda.sh 1 1 5 1 --lexer`
  reproduces the failure within a handful of iterations.
- Direct standalone reproduction of the exact grammar text has NOT
  reproduced (attempted 3 times with different grammars from failing
  runs).

## Next steps

- Preserve `random.alp` and `random.inputs` from a failing testcuda run
  by inserting a `trap` on the script's `return 1` to snapshot the job
  directory before it's cleaned up by the `EXIT` trap.
- Diff standalone-generated `.inputs` vs the captured one to test
  hypothesis (1).
- If hypothesis (2), reduce the failing input under the same binary
  (varying only input) and identify a minimal single-block reproducer.

## Regression bounds

- `main` before merge `64444f4` (i.e. `e84bac3`): `test-long-input.sh
  grammars/json.alp cuda` passed; `testcuda.sh` was known-broken at the
  sweep level per commit `e84bac3`'s message ("silently tested a single
  configuration").
- `main` at `64444f4`: `test-long-input.sh grammars/json.alp cuda`
  passes (verified pre-merge on the branch); `testcuda.sh` fails as
  described here.

The fusion correctness fix (`da47169`) is a strict improvement on the
per-grammar json regression path.  The testcuda random-grammar path is a
separate long-tail issue.
